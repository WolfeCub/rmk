# From v0.9 to v0.10

Use this guide to update an existing RMK v0.9 firmware project. For new projects, follow the current [processor guide](../features/processor).

## Processors

Update registration first, then choose whether to keep your existing run loop.

### Remove registration mode arguments

In each `keyboard.toml` keyboard module, replace `#[register_processor(event)]` or `#[register_processor(poll)]` with the bare attribute:

```diff
- #[register_processor(event)]
+ #[register_processor]
```

Registration now starts the type's `Runnable` implementation. Check the type's `#[processor]` options to preserve the behavior you want:

| Previous setup                                   | What to keep or change                                                                              |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `(poll)` with a polling processor                | Keep `poll_interval` and `poll()`.                                                                  |
| `(event)` with an event-only processor           | Keep `subscribe` without timer options.                                                             |
| `(event)` used to bypass the type's polling loop | Remove `poll_interval` to keep event-only behavior.                                                 |
| A type with a custom `Runnable`                  | Keep that implementation and its `#[runnable_generated]` marker; registration now starts your loop. |

Rust API projects that already use `run_all!` do not need a registration change.

### Use the generated deadline loop

Existing `DeadlineProcessor::deadline()` and `on_deadline()` methods keep their names. If you want RMK to generate the run loop for an existing deadline processor:

1. Add `deadline` to its `#[processor]` attribute.
2. Keep `deadline()` and `on_deadline()` in `impl DeadlineProcessor`.
3. Remove the old `impl Runnable` and `#[runnable_generated]` marker.

Keep the marker and `impl Runnable` if your custom loop is still needed. The [inactivity example](../features/processor#handle-inactivity) shows a complete processor with the generated loop.

## Battery setup

TOML charger keys keep their syntax. Rust API projects must now start the charger components separately from `BleTransport`.

### Move GPIO setup out of BleBatteryConfig

`BleBatteryConfig` controls central battery notifications. It no longer owns GPIO pins or has a lifetime parameter.

1. Replace `BleBatteryConfig::new(...)` in your `RmkConfig` with `BleBatteryConfig { enabled: true }` to enable notifications, or `BleBatteryConfig::disabled()` to disable them.
2. Move an existing charging-state pin into `ChargingStateReader::new(pin, low_active)`.
3. Move an existing charging LED pin into `BatteryLedProcessor::new(pin, low_active)`.
4. Run those components alongside one `BatteryProcessor` in your existing `run_all!` call. Omit a component if its old pin was `None`.
5. Replace explicit `BleBatteryConfig<'a>` type annotations with `BleBatteryConfig`.

Choose the processor constructor that matches your inputs:

| Inputs                                          | Constructor and tasks                                                     |
| ----------------------------------------------- | ------------------------------------------------------------------------- |
| ADC measurement, with or without charging state | Use `BatteryProcessor::new(measured, total)` and keep the ADC input task. |
| Charging state without ADC measurement          | Use `BatteryProcessor::charging_only()`.                                  |

For imports and a task-list fragment, see [using the Rust API](../configuration/wireless#using-the-rust-api).

### Keep existing TOML charger settings

The `[ble].charge_state` and `[ble].charge_led` fields keep their syntax. RMK constructs and runs the battery components for you; you do not need to add Rust GPIO setup.

Split boards can also configure those fields under `[split.central]` and `[[split.peripheral]]`. Check the [split battery configuration](../configuration/wireless#split-battery-configuration) before moving an existing setting: central overrides and peripheral settings have different fallback rules.
